# Threat model

SPEC §17 summarizes the security model; this document expands it (M7-05). For each threat
it names the mitigation, the task that implemented it and the tests that prove it, then lists
the residual risks we accept.

## Assets

| Asset | Where it lives |
|---|---|
| Master password, KEK | typed at unlock, never stored; KEK derived with Argon2id (or held by the OS keyring) |
| LMK and vault keys | in memory only while unlocked, in `mlock`ed pages (`hardening::Locked`), zeroized on lock |
| Item bodies (hosts, passwords, private keys, passphrases, snippets) | SQLite `items.envelope`, XChaCha20-Poly1305 under the vault key |
| Decrypted labels and search index | `TEMP` table / memory only (`temp_store = MEMORY`) |
| Account keys, sync tokens | `meta` / `sync_state`, AEAD under the LMK |
| Session contents | the terminal (not stored), encrypted recordings (§7.5) |
| Host keys (known_hosts) | vault items; integrity matters, not secrecy |
| Shared-terminal stream | E2EE frames; key only in the link fragment |

## Actors

- **Malicious or compromised server operator**: sees all ciphertext, the membership lists and
  the public-key directory; can drop, replay or reorder data.
- **Network attacker**: on the path to the sync server, an SSH host or a proxy.
- **Malicious remote host**: controls everything a session prints and every reply to sverb.
- **Malicious teammate** (or a compromised teammate account): can write items into shared
  vaults and see what those vaults hold.
- **Local attacker without an unlocked session**: has the disk (stolen laptop) or runs code
  as another user.
- **Local attacker with an unlocked session**: runs code as the same user while sverb is
  unlocked.

## `unsafe` policy

The workspace lint is `unsafe_code = "deny"` (SPEC §17 asked for `forbid`; `forbid` can't be
lifted by an inner `allow`, which the two exceptions need). Exactly two modules carry
`#![allow(unsafe_code)]`, with a `SAFETY` comment on every block:

1. `crates/sverb-core/src/hardening/{unix,windows}.rs`: `prctl(PR_SET_DUMPABLE)`,
   `setrlimit`/`getrlimit`, `mlock`/`munlock`, `sysconf`; `SetErrorMode`, `WerSetFlags`,
   `VirtualLock`. Plain libc/Win32 calls with integer arguments or pointers to values we own;
   none keeps a pointer. `hardening/mod.rs` (the page reference counting and `Locked<T>`) is
   safe code.
2. `crates/sverb-conn/src/agent/dacl_windows.rs`: the agent pipe's owner-only DACL (SDDL
   `D:P(A;;GA;;;<user SID>)`) and the client token SID comparison.

`scripts/check-unsafe.py` (CI job `unsafe-check`, tested by
`sverb-e2e/tests/forbid_unsafe.rs`) fails if the lint is lifted anywhere else, if a crate
overrides it, or if the workspace level is weakened. `forbid_unsafe.rs` also proves that every
crate inherits the `deny`.

## Process hardening details

- `harden_process()` is the first thing `main` does after installing the panic hook, before
  any secret exists. The report (no secrets) is logged at `debug`.
- `PR_SET_DUMPABLE 0` makes `/proc/<pid>/*` root-owned and blocks `ptrace` and
  `/proc/<pid>/mem` for same-user, non-root processes. It is reset by `execve`, so shells,
  `ProxyCommand` and `ssh-add` started by sverb behave normally.
- `Locked<T>` counts references per page, so freeing one key never unlocks a page another key
  shares. Values are zeroized before their pages are unlocked. When `RLIMIT_MEMLOCK` is too low
  the key stays usable and one `debug` line says so.

## Review checklist (one-time audit, M7-05)

- `expose()` / `expose_secret()` (142 non-test call sites): none inside a `tracing`,
  `print`/`panic` or `format!` macro, except the two share-link builders in
  `sverb-crypto/src/share.rs`, which put the key in the URL fragment by design (§14).
- `unwrap()` / `expect()` in non-test code: denied by clippy (`unwrap_used`, `expect_used`);
  the two allowed `expect`s (`sverb-crypto` `recovery.rs`, `canon.rs`) are invariants
  (32-byte BIP39 entropy; a canonical field longer than `u32::MAX`).
- `Debug` derives on types with plain secret fields: fixed in M7-05 for
  `RegisterStartRequest`, `RegisterFinishRequest`, `LoginFinishRequest` (`sverb-proto`),
  `CreatedInvite` (`sverb-server`) and `ApiDirectory` (`sverb-sync`), which now print
  `[REDACTED]`. Other secret fields use `SecretString` / `Key32` / `Zeroizing`.
- `info`+ logging of hosts: no `?ResolvedHost` or hostname/username field at `info`+ in client
  crates; `info`+ lines carry ids (UUIDs) only. The server logs its listen address and public
  URL at startup, and the one-time setup token (`warn`, by design: M4-01, the operator needs it
  to register the first account).

## Residual risks

- **Revoked members keep old data.** Removing a member rotates the vault key (M5-04), but
  whatever they synced or copied before is theirs.
- **Server-asserted membership.** Grants are trusted only with a valid signature by a pinned
  key, but the server's membership list decides who may grant (see M5-03 below).
- **First sight (TOFU)** of a teammate's key, until safety numbers are compared.
- **Debug logs contain hostnames.** `--debug` / `SVERB_LOG=debug` write hostnames to the log
  file (SPEC §17); `--debug` warns about it.
- **OSC 52 relies on the outer terminal.** Once the user allows a write, the outer terminal
  decides what it does with it.
- **Panic messages** go to crash reports unredacted (they are built from the `info`+ ring, but
  a panic message itself could contain data; M0-05 open question).
- **`mlock` is best effort**: not available with a low `RLIMIT_MEMLOCK`, and values copied
  before they reach `Locked` (stack temporaries, Argon2 buffers) are only zeroized, not locked.
- **Same-user attacker with an unlocked session** on macOS/Windows can still read process
  memory (no `PR_SET_DUMPABLE` equivalent); on Linux, root or `CAP_SYS_PTRACE` can.
- **Windows code is not compiled or run in this repository's local checks** (the DACL module,
  hardening on Windows); it is exercised only by the Windows CI job.
- **Canary coverage** is limited to the artifacts tests leave behind: tests that delete their
  temp dirs (most `tempfile` users) are scanned only if they fail to clean up; the binary
  fixture (`tests/canary.rs`) and `target/tmp` homes are always scanned. Per-test server
  databases are dropped by their tests, so the server dump usually covers only the shared one.

## Teams: server compromise and public-key substitution (M5-03)

### Server compromise: public-key substitution (SPEC §13.3, §17)

The sync server stores only ciphertext, but it is the directory of account public keys
(`GET /v1/users/{id}/public-keys`) and of org and vault membership. A malicious or compromised
server could try to substitute a member's keys, so that a vault key is wrapped to the attacker
(grant **to** a victim), or so that a grant signed by the attacker is accepted (grant **from** a
"member").

#### Mitigations (M5-03)

- **TOFU pinning.** Every user's keys are pinned on this device the first time they are seen
  (`pinned_keys`, client migration `0003`), whether while granting, listing members or verifying
  grants. Pins are device-local and never synced, so the server can't poison them through sync.
- **Key-change warning.** A key that differs from the pin does not replace it. It is recorded
  as a pending change, the ✓ is cleared, the member shows `⚠ key changed` with a red modal, grants
  **to** that user are blocked (`Trust::keys_for_grant`), and grants **from** that user are not
  trusted (`verify_grant`). This lasts until the user compares safety numbers and chooses "Accept
  new key". Account keypairs survive password changes and recovery (only the bundle is re-wrapped),
  so a legitimate change only happens when an account is re-created.
- **Safety numbers.** 60 digits in 12 groups, computed from the sorted pair of key fingerprints,
  so both members see the same number (`sverb team verify <user>`, Settings → Team). A user who
  compared them out of band marks the member verified (✓, device-local).
- **Grant verification.** A wrapped vault key is used only after both checks pass. First, its
  Ed25519 signature over the canonical grant encoding verifies with the **pinned** key of
  `wrapped_by`. Second, the granter has `manage` on the vault, is an org owner or admin, or is
  the vault's creator, according to the server's membership list. On top of that:
  - personal vault keys are accepted only as self-grants signed with this account's own key;
  - a self-grant claimed for another user is rejected unless that user is the vault creator;
  - unpinned granters and granters with a pending key change are rejected.

#### Residual risk

- **First sight.** TOFU trusts whatever key the server serves the first time a user is seen. A
  server that is malicious from the start can substitute a key before it is pinned. Only comparing
  safety numbers out of band (✓) detects that. Members who never verify each other are exposed
  to it.
- **Membership is server-asserted.** The org role and vault permission lists come from the
  server. The client uses them only to *narrow* trust: a grant still needs a valid signature by a
  pinned key. However, a malicious server can claim that a pinned member (for example a former
  admin, or any member it chooses) has `manage`, or that some user is the vault creator. A grant
  that member really signed would then be accepted. The server can't forge grants, but it can
  replay or misattribute authority among real, pinned members.
- **Vault creator TOFU.** The first self-grant of a shared vault is trusted on first sight. The
  server chooses which user it calls the creator, within the set of keys that are already pinned
  or that it serves at first sight.
- **Per-device trust.** Pins and ✓ are per device and are not synced. A new device starts with
  no pins and repeats TOFU. Verify members again on each device that matters.
- **Accepting a changed key** without actually comparing the new safety number defeats the
  warning. The UI and CLI always show the new number and ask before accepting.
